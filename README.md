# LoveHub ❤️ — Private Couple App

LoveHub is a private couple companion web app: a personal chat for two,
shared memories, relationship milestones, love-themed mini-games, a music
room, an AI love assistant, and more — all behind one shared couple account.

- **Stack:** plain HTML/CSS/JS (no framework, no build step for dev),
  Supabase (Postgres + Auth + Realtime + Storage).
- **Deploy:** static output generated by `scripts/build.sh` into `dist/`
  (Vercel / any static host).

---

## Architecture overview

```
index.html          Single-page shell (all views are <section data-page>)
app.js              Legacy UI controller (LoveHub class) — pages, auth UI,
                    profile, memories, games, login/settings flows
chat-rich.js        Additive prototype wraps over app.js — rich chat,
                    media messages, voice, drawings, stickers, backgrounds,
                    music room, AI assistant
style.css           Core theme + layout (dark romantic identity)
chat-rich.css       Rich-chat styles
chat-rich-fixes.css Post-launch CSS fixes (kept separate, additive)
data.js             Static demo content (games, memories, milestones)
utils.js            Shared helpers (formatting, storage, escapeHtml, toast)
icons.js            Inline SVG icon registry
stickers.js         Sticker catalog
sw.js               Service worker — notifications + offline asset cache
src/main.js         ES-module boot: owns the single Supabase auth listener,
                    instantiates the active service layer, publishes state
                    to the legacy UI shell
src/services/       ACTIVE service layer (ES modules, Supabase-backed)
services/           LEGACY service layer (classic scripts, demo fallback) —
                    see docs/SERVICE_MIGRATION_PLAN.md
supabase/           SQL migrations (apply in order), config examples, docs
assets/             Static images + vendored supabase-js
scripts/build.sh    Static production build (generates dist/supabase/config.js)
```

### Two service layers (short version)

| Layer | Status | Purpose |
|---|---|---|
| `src/services/*` | **Active** | ES modules used by `src/main.js`: `AuthService`, `ProfileService`, `CoupleService`, `ChatService`, `NotificationService`, `SoundService`, `SupabaseClient`. Single source of truth for auth + data. |
| `services/*` | Legacy | Classic scripts loaded by `index.html`: `StorageService` (localStorage wrapper, still used by active `AuthService`), `AuthService` (demo accounts, dev-mode-only), `UserService`/`HealthService` (demo data), `SupabaseService`/`LocalizationService` (dead — no references). |

Full audit + migration plan: **`docs/SERVICE_MIGRATION_PLAN.md`**.

### Auth & session model (why there are no race conditions)

- **One auth owner:** `src/main.js` creates the single `AuthService`, installs
  exactly one Supabase `onAuthStateChange` listener, and queues events until
  the legacy UI shell signals ready (`LoveHubMarkAppReady`).
- **One boot promise:** `AuthService.initialize()` shares a single
  `_initializePromise`, so `app.js` and `main.js` can never race two
  independent session reads.
- **Serialized handling:** `app.js → handleSignedIn` uses a busy/queued flag
  plus a generation counter, so a slow profile/couple load can never restore
  a user after a `SIGNED_OUT` event.
- **Demo mode is dev-only:** the legacy demo accounts are gated behind
  `isDevMode()` (localhost / `file:` / `?demo=1`) and are never persisted
  with passwords. On any real deployment the Supabase path is the only one.

## Development setup

1. **Serve the repo** (any static server works):
   ```sh
   python3 -m http.server 8080        # or: node scripts/serve.js
   ```
   Or use the Freebuff preview — it serves the live filesystem.

2. **Backend (optional for real accounts):**
   - Create a Supabase project.
   - Apply migrations in order — see **`supabase/migrations/README.md`**
     (this is the source of truth; `supabase/schema.sql` is a stale legacy
     file and must NOT be used).
   - `cp supabase/config.example.js supabase/config.js` and fill in
     `url` + `anonKey` from **Project Settings → API**.
   - `supabase/config.js` is git-ignored — real keys are never committed.
   - Without `supabase/config.js`, the app boots in **demo mode** (two
     hardcoded local accounts, development only).

3. **Auth redirects:** configure Site URL + Redirect URLs in
   Supabase → Authentication → URL Configuration for each environment
   (see `supabase/README.md`).

## Deployment

- **Build:** `scripts/build.sh` copies the app into `dist/` and generates
  `dist/supabase/config.js` from `SUPABASE_URL` + `SUPABASE_ANON_KEY`
  (fails loudly if either is missing — it never ships a demo-only site).
- **Vercel:** `vercel.json` pins `buildCommand: sh ./scripts/build.sh` and
  `outputDirectory: dist`. Set `SUPABASE_URL` + `SUPABASE_ANON_KEY` as
  project environment variables (Production, Preview, Development).
- **Freebuff hosting:** same build; set the two env vars as deployment env
  vars.
- Always use the **anon/public** key in frontend config — never the
  `service_role` key.

## Security notes (Phase 1 hardening)

- No secrets are committed: `supabase/config.js`, `.env*`, and logs are
  git-ignored; the only config in the repo is a placeholder example.
- Demo accounts are dev-mode-only and never persist passwords.
- All chat writes go through security-definer RPCs; reads are RLS-scoped to
  confirmed couple members (see `supabase/migrations/README.md`).
- User content rendered in chat bubbles is HTML-escaped before injection.
- Committed `server_output.log` was removed; logs are now ignored.
